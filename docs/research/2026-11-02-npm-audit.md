# npm audit triage, 2026-11-02

`npm audit` on main (v0.37.0): 41 findings (1 critical, 6 high, 34 moderate). After the dompurify
bump: 40 (0 critical). `npm audit --omit=dev` lists only electron and its extract-zip; the rest is
dev and build tooling (eslint, electron-builder, vite, jsdom) and is not covered here.

## 1. dompurify: fixed, 3.4.15 → 3.4.17

- The lockfile had 3.4.15, not 3.4.16.
- dompurify is not used by `NewsSection.tsx`. Its only call site is
  `src/renderer/src/lib/updateNotes.ts`, which sanitizes the GitHub release body that
  `UpdateDialog.tsx` renders with `dangerouslySetInnerHTML`. News renders as React text, and news
  links are filtered to http(s) by `httpUrl()` in `src/main/sources/sleeperNews.ts`.
- Fixed versions: GHSA-p98j-92pf-mc4p and GHSA-6688-9rhm-gjv2 in 3.4.16; GHSA-cg2g-xh64-v4q7,
  GHSA-mrv2-3pqr-j5jr and GHSA-c6gr-qvv4-5v3f in 3.4.17. That makes **3.4.17** (2026-10-12) the
  first release that fixes all five.
- Actual exposure was low. Every advisory needs a mode the app does not use (`IN_PLACE`,
  `SAFE_FOR_TEMPLATES` with DOM output, or `PARSER_MEDIA_TYPE: application/xhtml+xml`). The app calls
  `sanitize()` with string output and a tag/attribute allowlist, on release notes from its own repo.
- Checked with the updateNotes, UpdateDialog, NewsSection and newsView tests, the full suite
  (1277 passed, 6 skipped), typecheck and eslint.

## 2. Electron: not upgraded

The app is on **39.8.10** (Node 22.22.1, Chromium 142). The 39 line ended with that release on
2026-05-05, so **no 39.x patch exists for any of these advisories**. Supported lines are 43, 44 and 45.

How the app is set up (`src/main/index.ts`, `src/renderer/index.html`):

- It has one `BrowserWindow` with `contextIsolation: true`, `nodeIntegration: false` and
  `sandbox: false`.
- `setWindowOpenHandler` passes the URL to `shell.openExternal` and always returns
  `{ action: 'deny' }`, so the app never creates a child window.
- It loads only its bundled `index.html`, under the CSP `default-src 'self'`.
- It has no `<webview>`, no iframes, no `protocol.register*`, no extensions and no permission
  handlers. It uses no HID, USB, pointer lock, offscreen rendering or frame subscription.

**Why eMudhra matters for this app.** The fix blocks the compromised intermediates in both
Chromium networking and Node `tls`/`https`/`fetch`, and the app uses both:

- The data sources (Sleeper, FantasyPros, FantasyCalc, nflverse) use the main process's `fetch`.
- electron-updater uses Electron's `net`.

The installers are unsigned, and `electron-builder.yml` sets no `publisherName`, so electron-updater
does not verify a signature. An update's integrity rests on the sha512 in `latest.yml`, which comes
over the same TLS connection. An attacker with a certificate from those intermediates and an
on-path position could serve a modified update. Both conditions are needed, so the risk is low, but
the impact is code execution. There is no app-side workaround. Fixed in 42.11.16+, 43.8.1+, 44.9.1+
and 45.0.0+.

These are not advisories, but they are worth a separate change:

- `sandbox: false` leaves the preload with Node access.
- With no `session.setPermissionRequestHandler`, Electron grants permission requests by default.
- `setWindowOpenHandler` passes any URL scheme to `openExternal`. Inputs are filtered today (news by
  `httpUrl`, release notes by DOMPurify's URI allowlist), but an http(s) check in the handler would
  close it at the source.

### What a major upgrade involves

Target **45.x** (45.2.1: Node 24.22.1, Chromium 156). It has the longest support window, and its
breaking changes do not touch this app (see the 45 entry below). 44.10.1 ships the same Node.

Breaking changes from 40 to 45 that touch this app (Electron `docs/breaking-changes.md`):

- **42: `electron` no longer downloads its binary in `postinstall`.** It now downloads on first run of
  its bin. Check that `npm run dev` (electron-vite) and CI's `npm ci` still find the binary. If they
  don't, run the package's `install-electron` script from `postinstall`. electron-builder fetches its
  own Electron dist for packaging.
- **43: dialogs default to the Downloads folder.** This affects `showSaveDialog` in
  `src/main/ipc/handlers.ts` and `showOpenDialog` in `src/main/dev/ipc.ts` unless they set
  `defaultPath`.
- **44: `clipboard` methods return Promises.** `clipboard.writeText` in `src/main/dev/ipc.ts` should
  be awaited. The renderer has no clipboard use. ia32 builds were dropped (the app ships x64).
- **45: sandboxed-preload and `window.open` child changes.** Neither applies (`sandbox: false`, all
  popups denied).

The runtime moves from Node 22.22.1 to 24.22.1 in the main process and worker threads:

- **`node:sqlite`** (`src/main/db/connection.ts`) is still experimental in Node 24. vitest runs on
  the system Node from `.nvmrc` (22), not on Electron's Node. Move `.nvmrc`, `engines` and
  `@types/node` to 24 in the same change, so the suite and CI (`node-version-file: .nvmrc`) exercise
  the Node major the app ships with.
- **`@duckdb/node-api` 1.5.6-r.1** uses prebuilt N-API bindings (`@duckdb/node-bindings-win32-x64`),
  with `npmRebuild: false` and the bindings asar-unpacked. N-API is stable across ABI versions
  (`modules` 140 → 150), so no rebuild is expected. It still needs a smoke test in the packaged app,
  because DuckDB runs in a worker thread (`src/main/stats/client.ts`).
- **electron-builder** 26.15.3 and **electron-updater** 6.8.9: no change expected.
- **electron-vite** 5.0.0: its target table stops at Electron 39. For newer versions it falls back
  to 39's targets (node22.20 / chrome142). That is harmless because it only transpiles more.
  electron-vite 6.0.0 has newer targets, but check its vite peer range first.

Before releasing, verify:

- typecheck, eslint and the full suite on Node 24
- a `build:win` installer, installed on Windows
- a smoke test: launch, league refresh, stats sync (DuckDB), update check and dialog, CSV export
  (save dialog), and the dev-notes copy (clipboard)

## 3. vitest: dev-only

GHSA-qxg6-89mg-rqv8 and GHSA-xp26-3454-mjgp are in `@vitest/mocker` from 5.0.0-beta.1 to 5.0.2 and
are fixed in 5.0.3. They affect the test runner only and nothing ships.

The bump is not a pure patch with npm 10.9.8:

- **Pinning 5.0.x fails.** `npm install -D vitest@5.0.3` (and 5.0.4, 5.0.5, `~5.0.5`) crashes in
  arborist with `Cannot read properties of null (reading 'edgesOut')`.
- **`npm install -D vitest@^5.0.5` works.** It resolves cleanly to **5.1.0**, changing one line in
  `package.json` and about 120 lines of lockfile:
  - vitest, `@vitest/mocker` and `@vitest/spy` go to 5.1.0.
  - chai 6.3.0, obug 3.0.0, std-env 4.3.0, tinybench 6.2.3, tinyexec 1.3.1, magic-string 1.4.5,
    why-is-node-running 3.2.1.
  - siginfo and stackback are removed.
- **5.1.0 was tested, then reverted.** The full suite passed (1277 passed, 6 skipped) and typecheck
  was clean, and `npm audit` no longer lists vitest.

So the bump is trivial if you accept the 5.1 minor.
